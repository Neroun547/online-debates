Архітектура

Модульна архітектура. Модулі бувають 2 типів, інфраструктурні та доменні. 

інфраструктурні модулі відповідають за роботу з БД, сторонніми інтеграціями (наприклад поштовий сервіс)

Модулі для роботи з бд зберігаються в папці db
Модулі для сторонніх інтеграцій зберігаються в папці integrations

Доменні модулі відповідають за саму бізнес логіку тої чи іншої сутності або бізнес процесу (наприклад: користувач, управління категоріями, слотами і т.д).

Між доменною та інфраструктурною логікою є мапери. За допомогою мапері доменна логіка комунікує з інфраструктурою 

WebRTC

Для кожної сесії у нас є свій унікальний роутер. В кожного користувача є 2 транспортери на бекенді для отримання та відправлення данних і такі самі 2 на фронтенді.

Транспортер для відправки данних використовує producers для відправки данних (на кожний потік данних свій producer). Producers сторюються на бекенді, на фронтенді просто визивається метод produce у транспортера 

Транспортер для отримання данних використовує consumers для отримання данних (на кожен потік свій consumer). Consumers створюються на бекенді, на фронтенді просто визивається метод consume

Як воно працює ?

1. Спочатку клієнт створює sendTransporter. 

З клієнту викликається метод init який перевіряє чи вже запущено WebRTC сервер чи ні ? Якщо не запущено то запускає.

Далі створюється router (якщо ще немає для цієї сесії) під конкретну сесію та зберігається в пам'яті додатку на бекенді.

Далі створюється транспортер для клієнту (якщо немає). Данні про транспортер передаються на фронтенд

2. Отримані данні про транспортер використовуються для створення транспортеру вже на фронтенді. 

Береться девайс користувача на фронтенді і до нього підв'язується цей транспортер.

Далі підключаємо цей транспортер стоврений на фронтенді до транспортеру на бекенді.

3. Далі ми беремо аудіо та відео потоки користувача та для кожного створюємо свій producer.

На фронтенді у транспортера викликаємо метод produce для аудіо та відео.

Метод produce викликає подію "produce" у transporter в цій події ми робимо запит на бекенд і на бекенді вже створюємо producers та зберігаємо produceVideoId та produceAudioId для конкретного користувача.

Цей метод на бекенді відправляє подію по WebSocket для іншого користувача в якому вказує інформацію про створений producer.

4. Інший користувач отримує цю подію та створює transporter на бекенді, потім на фронтенді через device, а потім підключає цей transporter, створений на фронтенді, на бекенді для отримання данних. 

5. Робимо запит на бекенд для створення consumer. Перед цим перевіряємо чи може цей consumer отримувати данні, якщо так то створюємо його та зберігаємо.

Для конкретного користувача, робимо обробку подій цього consumer для видалення цього consumer якщо transport або producer були закриті.

Відправляємо данні на фронтенд та на фронтенді свторюємо consumer з цього consumer отримуємо потік аудіо/відео та додаємо у MediaStream, цей MediaStream виводимо в html video.

Робимо обробники подій якщо потік припинеться або transport перестане існувати в них видаляємо consumer. 

Робимо запит на бек щоб зняти з паузи consumer (на беці він створювався з паузою щоб фронтенд встиг створити його на своїй стороні)

Також я додав метод getProducerData який викликається під час завантаження сторінки для того щоб отримати данні наявних producers (якщо вони вже були створені)
